## Тест-кейсы

### TC-01. Успешное бронирование — Приоритет: H

**Шаги:**
1. Выбрать комнату «Средняя».
2. Указать завтрашнюю дату.
3. Начало `10:00`, окончание `11:30`.
4. Участники `6`.
5. Имя `Иван Петров`, почта `ivan.petrov@company.ru`.
6. Нажать «Забронировать».

**Ожидаемый результат:** сообщение «Бронирование создано», в нём: Средняя, завтрашняя дата, `10:00–11:30`, Иван Петров. Ошибок под полями нет.

### TC-02. Пустые обязательные поля — Приоритет: H

**Шаги:**
1. Ничего не заполняя, нажать «Забронировать».

**Ожидаемый результат:** под каждым из 7 полей — сообщение об ошибке, общий статус «Проверьте, пожалуйста, заполнение формы», бронь не создана.

**Повторить для каждого поля отдельно:** заполнить всё, кроме одного поля → ошибка только под этим полем.

### TC-03. Дата в прошлом — Приоритет: H

**Шаги:**
1. Заполнить все поля корректно, но датой вчера.
2. Нажать «Забронировать».

**Ожидаемый результат:** ошибка «Дата не может быть в прошлом.», бронь не создана.

### TC-04. Окончание раньше/равно началу — Приоритет: H

**Шаги:**
1. Заполнить все поля корректно; начало `14:00`, окончание `13:00`.
2. Нажать «Забронировать».
3. Повторить с окончанием, равным началу (`14:00–14:00`).

**Ожидаемый результат:** ошибка «Время окончания должно быть позже начала.», бронь не создана (в обоих случаях).

**Фактический результат:** для `13:00 < 14:00` ошибка показывается; для `14:00–14:00` бронь создаётся (BUG-03, частный случай BUG-02 — нулевая длительность).

### TC-05. Участников больше вместимости — Приоритет: H

**Шаги:**
1. Выбрать «Малая», участников `10`, остальные поля корректны.
2. Нажать «Забронировать».
3. Повторить для «Средняя» + 15 и «Большая» + 25.

**Ожидаемый результат:** ошибка о максимальной вместимости выбранной комнаты, бронь не создана.

**Фактический результат:** ошибка показывается, бронь не создаётся, но текст содержит грамматическую ошибку: «В комнате максимум 10 участника.» (BUG-04). Для «Большая» + 25 текст «Количество участников — от 1 до 20.» — допустимо, т.к. 25 вне общего лимита.

### TC-06. Прошедшее время для сегодняшней даты — Приоритет: M

**Шаги:**
1. Выбрать сегодняшнюю дату.
2. Начало и окончание — прошедшие часы (например, `09:00–10:00` при текущем времени после 10:00).
3. Остальные поля корректны, нажать «Забронировать».

**Ожидаемый результат:** ошибка, бронь не создана.

### TC-07. Участники вне диапазона 1–20 — Приоритет: M

**Шаги:**
1. Выбрать «Большая» (вместимость 20), участников `0`, остальные поля корректны → «Забронировать».
2. Повторить с участниками `21`.

**Ожидаемый результат:** ошибка «Количество участников — от 1 до 20.», бронь не создана.

### TC-08. Формат почты — Приоритет: M

**Шаги:**
1. Заполнить все поля корректно, почта `ivan.company` (без @ и домена) → «Забронировать».
2. Повторить с `ivan@company` (домен без зоны) и `ivan@.ru`.

**Ожидаемый результат:** ошибка «Введите корректную рабочую почту.», бронь не создана.

### TC-09. Длительность вне 30 мин–4 ч — Приоритет: M

**Шаги:**
1. Заполнить все поля корректно, время `10:00–10:20` (20 минут) → «Забронировать».
2. Повторить с `10:00–15:01` (более 4 часов).

**Ожидаемый результат:** ошибка о недопустимой длительности, бронь не создана.

### TC-10. Данные не сохраняются после перезагрузки — Приоритет: M

**Шаги:**
1. Успешно забронировать (TC-01).
2. Нажать F5.

**Ожидаемый результат:** все поля пустые, сообщение об успешной брони исчезло. Данные нигде не отображаются.

### TC-11. Границы длительности: ровно 30 мин и ровно 4 ч — Приоритет: L

**Шаги:**
1. Корректная бронь с `10:00–10:30` → «Забронировать».
2. Повторить с `10:00–14:00`.

**Ожидаемый результат:** обе брони создаются (границы включены).

### TC-12. Участники ровно на границе вместимости — Приоритет: L

**Шаги:**
1. «Малая» + 4 участника, корректные поля → «Забронировать».
2. Повторить: «Средняя» + 10, «Большая» + 20.

**Ожидаемый результат:** все брони создаются.

### TC-13. Ошибка исчезает при исправлении поля — Приоритет: L

**Шаги:**
1. Отправить пустую форму — под полями ошибки.
2. Начать заполнять поля корректными значениями.

**Ожидаемый результат:** ошибка под полем исчезает сразу при вводе, общий статус ошибки очищается.

### TC-14. Пробелы в имени и почте — Приоритет: L

**Шаги:**
1. Заполнить все поля, имя из одних пробелов `   ` → «Забронировать».
2. Повторить с именем и почтой с пробелами по краям: ` Иван ` / ` ivan@company.ru `.

**Ожидаемый результат:** (1) ошибка «Укажите имя.»; (2) по требованиям не определено — зафиксировать фактическое поведение, при необходимости вопрос аналитику.

**Фактический результат:** (1) ошибка «Укажите имя.» показывается; (2) пробелы по краям обрезаются — бронь создаётся с именем `Иван` и почтой `ivan@company.ru`, в подтверждении значения без пробелов. Соответствует ожиданиям, вопрос аналитику снимается.

### TC-15. Минимальная дата в календаре — Приоритет: L

**Шаги:**
1. Открыть календарь поля «Дата».

**Ожидаемый результат:** прошедшие даты недоступны для выбора; минимальная доступная дата — сегодняшняя.

## Дефекты

> Оформляются по итогам прогона: условия, шаги, ожидаемый/фактический результат, приоритет с обоснованием, скриншот в `docs/screenshots/`.

### BUG-01. Прошедшее время для текущего дня не отклоняется — Приоритет: High

- **Условия:** страница открыта, текущее время позже 10:00.
- **Шаги:** TC-06.
- **Ожидаемо:** ошибка, бронь не создана (требование: «для текущего дня нельзя выбрать прошедшее время»).
- **Фактически:** сообщение «Бронирование создано», прошедший интервал принят.
- **Обоснование приоритета:** нарушает прямое требование; можно «забронировать» встречу в прошлом.
- **Доказательство:** `docs/screenshots/bug-01-past-time-today.png`.

### BUG-02. Длительность не проверяется (0 минут и более 4 часов проходят) — Приоритет: High

- **Условия:** страница открыта.
- **Шаги:** TC-09 и TC-11 (пограничные значения 30 мин / 4 ч тоже не отделяются).
- **Ожидаемо:** длительность вне 30 мин–4 ч отклоняется (требование: «длительность от 30 минут до 4 часов»).
- **Фактически:** проходят 0 минут (`10:00–10:00`), 20 минут, более 4 часов; границы не проверены, т.к. логики проверки нет вовсе (в `script.js` отсутствует).
- **Обоснование приоритета:** нарушает прямое требование; возможна бронь на сутки и «пустая» бронь.
- **Доказательство:** `docs/screenshots/bug-02-duration-20min.png`, `docs/screenshots/bug-02-duration-5h30.png`.

### BUG-03. Окончание, равное началу, принимается — Приоритет: Medium

- **Условия:** страница открыта, остальные поля корректны.
- **Шаги:** TC-04, вариант 2: начало `14:00`, окончание `14:00` → «Забронировать».
- **Ожидаемо:** ошибка «Время окончания должно быть позже начала.», бронь не создана (в script.js сравнение `endTime < startTime` не покрывает равенство; плюс требование минимальной длительности 30 минут из BUG-02).
- **Фактически:** сообщение «Бронирование создано», бронь с нулевой длительностью подтверждается.
- **Обоснование приоритета:** следствие BUG-02 (нулевая длительность — крайний случай той же отсутствующей проверки); отдельно от BUG-02 выделен, потому что падает на другой ветке валидации (сравнение времени, а не длительность).
- **Доказательство:** воспроизводится шагами TC-04 (результат зафиксирован выше); поведение подтверждено автопрогоном.

### BUG-04. Грамматическая ошибка в сообщении о вместимости — Приоритет: Low

- **Условия:** страница открыта.
- **Шаги:** TC-05, вариант 2: «Средняя», участников `15` → «Забронировать».
- **Ожидаемо:** «В комнате максимум 10 участников.» (число 10 → «участников»).
- **Фактически:** «В комнате максимум 10 участника.» — в script.js строка статична (`участника`), склонение отсутствует; воспроизводится для «Малая» (4) и «Средняя» (10).
- **Обоснование приоритета:** только текст ошибки, функциональность не затронута, но ошибка видна пользователю в каждом срабатывании валидации вместимости.
- **Доказательство:** `docs/screenshots/bug-04-capacity-wording.png`.

## Вопросы и допущения

1. Длительность больше 4 часов и меньше 30 минут BUG-02 зафиксирован; должны ли границы 30 мин / 4 ч включаться?
2. Пересечения броней одной комнаты не проверяются: это вне MVP или упущение?
3. Формат отображения даты в сообщении об успешном бронировании: ожидаемо как в поле ввода (YYYY-MM-DD)?
4. Форма устанавливает минимальную дату один раз при загрузке страницы и не обновляет её после смены суток. Если вкладку открыть вечером и не перезагружать до утра, после полуночи форма без ошибки примет бронь на уже прошедшую дату; правильное значение появится только после F5. Кейс не проверялся (нужен прогон через полночь), риск оценён как низкий: вкладка с формой редко остаётся открытой через полночь.

## Проверенные области, риски и ограничения

- **Проверено:** клиентская валидация всех полей, граничные значения вместимости и участников, тексты ошибок и сообщения успеха, поведение после перезагрузки.
- **Не проверено:** пересечения броней, сохранение данных (нет бэкенда — отправка и сохранение отсутствуют по дизайну страницы), мобильная вёрстка, кросс-браузерность (только Chrome), локализация, доступность (a11y) поверх базовых role/label.
- **Риски:** вся валидация клиентская, серверные проверки отсутствуют; дата/время берутся из локальной машины пользователя.

## Инструкция запуска автотестов

Основной вариант (Docker):

```bash
docker compose run --build --rm tests
```

Резервный (без Docker):

```bash
python -m pip install -r requirements.txt
python -m playwright install chromium
python -m pytest
```

Отчёты: `artifacts/junit.xml` (для CI), скриншоты и trace при падении — `artifacts/browser/`, результаты Allure — `artifacts/allure-results/`.

Просмотр Allure-отчёта (нужен Allure Commandline, `scoop install allure` или с https://github.com/allure-framework/allure2/releases):

```bash
allure serve artifacts/allure-results
```
